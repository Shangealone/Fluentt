# FLUENTT v0.1 Development Design Specification

**Project:** FLUENTT: An Adaptive Language Learning System with Enhanced Spaced Repetition and NLP-Driven Pronunciation Modeling  
**Design version:** 1.0  
**Date:** 2026-09-21  
**Status:** Approved by the user on 2026-09-21; implementation planning authorized.

## 1. Purpose

FLUENTT v0.1 establishes the technical foundation for a research-oriented mobile language-learning system. The release must support a complete learner-facing vocabulary workflow, controlled participant accounts, bilingual interface localization, reliable online/offline review capture, reproducible research logging, and a backend scheduling abstraction that can later host both a conventional spaced-repetition baseline and the proposed FLUENTT Enhanced Spaced Repetition (ESR) algorithm.

v0.1 is a foundation release. It must not implement the final ESR mathematics, pronunciation scoring, NLP/conversational AI, educator/admin dashboards, formal experimental assignment, or statistical analysis.

## 2. Success Criteria

FLUENTT v0.1 is successful when a researcher-provisioned learner can:

1. Sign in using an assigned email address and temporary password.
2. Be required to replace the temporary password on first login.
3. Choose an interface language and a target learning language.
4. Open manually curated lessons and vocabulary content.
5. Study vocabulary and complete a basic review session.
6. Have correctness, response time, review metadata, scheduler type, and algorithm version recorded.
7. Continue eligible cached review activity during temporary loss of connectivity.
8. Synchronize offline review events without duplicate server records when connectivity returns.
9. View a basic progress summary.
10. Change supported preferences and sign out securely.

The release must also pass automated tests for authentication, authorization, content retrieval, review persistence, response-time capture, duplicate-safe synchronization, localization, and research-event recording.

## 3. Locked Technology Direction

### 3.1 Mobile application

- React Native
- Expo
- TypeScript
- Expo Router for application navigation
- Expo SecureStore for sensitive authentication/session material
- Expo SQLite for cached structured data and the offline synchronization queue
- English and Tagalog interface localization from the start
- Android and iOS as application targets, with Android as the primary development/test platform until iOS device access is available
- Expo/EAS may be used later for cloud builds, but public store deployment is outside v0.1

### 3.2 Backend

- Python
- FastAPI
- PostgreSQL as the authoritative server database
- SQLAlchemy 2.x-style ORM patterns
- Alembic database migrations
- Pydantic request/response validation
- JWT-based access and refresh sessions
- Argon2id password hashing

### 3.3 Versioning rule

At project initialization, implementation must use stable, mutually compatible versions of the selected frameworks and libraries. Exact versions must be pinned in lock/dependency files and documented in the repository. Dependency upgrades must not occur silently during a frozen research build.

## 4. Architectural Style

FLUENTT uses a client-server architecture with FastAPI as the single application gateway.

```text
React Native + Expo
        |
      HTTPS
        |
     FastAPI
        |
  +-----+-------------------------------+
  |     |          |          |         |
 Auth  Users     Content    Reviews    Sync
                         |      |         |
                         |  Scheduling   |
                         |      |         |
                         +-- Research Logging
                                |
                            PostgreSQL
```

The mobile application communicates only with FastAPI for authoritative application behavior. The mobile client must not connect directly to PostgreSQL or directly invoke future NLP/pronunciation providers.

FastAPI remains the integration boundary for future ESR, NLP, pronunciation, analytics, and external AI services.

## 5. User Scope

### 5.1 v0.1 role

Only the **Learner** role is supported in the mobile application.

### 5.2 Account creation

- Public self-registration is disabled.
- Study accounts are provisioned by the researchers through a controlled backend command/script.
- Each account receives:
  - an internal UUID;
  - a participant code such as `P001`;
  - an email address;
  - a temporary password;
  - an active/inactive status.
- The learner must change the temporary password after first successful login.

### 5.3 Password recovery

v0.1 does not require an external email-delivery provider. Forgotten passwords are reset through a researcher-controlled reset operation that issues a new temporary password and again requires password replacement at the next login.

## 6. Authentication and Session Security

1. Passwords are never stored in plaintext.
2. Password hashes use Argon2id.
3. FastAPI issues short-lived access tokens and rotatable refresh tokens.
4. Refresh-token state must be revocable server-side; stored token material on the server must not require plaintext refresh tokens.
5. Mobile sensitive token/session material is stored in Expo SecureStore, not SQLite or ordinary key-value storage.
6. Protected API routes reject missing, expired, revoked, or invalid sessions.
7. Production/research deployments require HTTPS.
8. Authentication responses must avoid revealing whether an email address exists when such disclosure is unnecessary.
9. Application logs must not record passwords, raw tokens, or other secrets.

## 7. Localization and Language Model

FLUENTT separates **interface language** from **target learning language**.

Example combinations include:

- Tagalog interface + English learning content
- English interface + Tagalog learning content

v0.1 must provide English and Tagalog interface resource files and must not hard-code user-facing strings throughout screen components.

The content model must be language-aware. English and Tagalog are supported structurally in v0.1, but the language used in the formal thesis experiment will be finalized separately after client consultation. That later research choice must not require a database or mobile architecture redesign.

## 8. Manually Curated Learning Content

v0.1 uses manually curated content. AI-generated learning content is outside scope.

Researchers manage content through seed/import scripts or controlled backend utilities; no educator/admin content-management UI is required in v0.1.

Minimum content hierarchy:

```text
Language
  -> Lesson
      -> Vocabulary Item
```

Minimum vocabulary properties:

- stable item UUID
- language
- word/term
- definition
- example sentence
- difficulty classification
- optional category
- optional translation
- active/inactive state
- content version

Content used in research must later be version-frozen so material does not change during formal data collection.

## 9. Mobile Feature Scope

### 9.1 Required screens/flows

- Splash / app initialization
- Login
- Required first-login password change
- Initial language/preferences setup
- Home
- Lesson list
- Lesson/vocabulary study view
- Review session
- Review result/feedback
- Progress summary
- Settings
- Offline/synchronization status

### 9.2 Home

The home screen must provide only useful v0.1 information:

- learner greeting;
- due/basic review count if available;
- recent/basic progress;
- quick path to continue learning/review.

No advanced recommendation engine or AI dashboard is required.

### 9.3 Progress

Basic progress may include:

- number of vocabulary items studied;
- number of completed review attempts;
- correctness summary;
- recent review activity.

Formal statistical research analytics are outside v0.1.

## 10. Backend Module Boundaries

The backend must be modular. API routes must remain thin and delegate to services/domain modules.

Recommended boundaries:

```text
backend/app/
  auth/
  users/
  content/
  reviews/
  scheduling/
  sync/
  analytics/
  research_logging/
  database/
  core/
```

### 10.1 Auth

Responsible for credential verification, token issuance/refresh/revocation, temporary-password enforcement, and researcher-initiated account/reset operations.

### 10.2 Users

Responsible for learner profile data and preferences.

### 10.3 Content

Responsible for languages, lessons, vocabulary items, and content retrieval/version metadata.

### 10.4 Reviews

Responsible for starting/closing review sessions, validating submitted attempts, persisting attempts, invoking the scheduler, and returning the accepted next-review state.

### 10.5 Scheduling

Exposes a stable scheduling interface. v0.1 implements only a clearly labeled development scheduler sufficient to exercise the end-to-end workflow.

The scheduling implementation must not be embedded directly inside API routes.

### 10.6 Sync

Responsible for receiving offline-created events, validating event ownership/content references, enforcing idempotency, and returning synchronization acknowledgement/results.

### 10.7 Analytics

Responsible only for basic learner-facing progress summaries in v0.1.

### 10.8 Research logging

Responsible for append-oriented, analysis-relevant event records. It is separate from operational/application logging.

## 11. Scheduling Abstraction

The review service depends on a scheduler contract rather than a hard-coded algorithm.

Conceptual contract:

```text
schedule(review_context) -> scheduling_result
```

The context must be able to carry at least:

- learner/internal participant reference;
- vocabulary item;
- correctness;
- response time;
- item difficulty;
- prior scheduling state/history when available;
- interaction timestamp.

The result must be able to carry at least:

- scheduler type;
- algorithm version;
- next interval;
- next due timestamp;
- updated scheduler state when applicable.

v0.1 scheduler identity:

```text
scheduler_type = development
algorithm_version = dev-0.1
```

Future strategies must be swappable behind the same contract:

- `conventional_srs`
- `fluentt_esr`

The final ESR mathematics are explicitly outside v0.1.

## 12. Response-Time Measurement

Learner response time is measured on the device, not inferred from server round-trip timing.

Measurement rule:

1. Start a monotonic/high-resolution elapsed-time measurement when a review prompt becomes fully visible and interactable.
2. Stop the measurement when the learner commits the final answer.
3. Store/send the elapsed duration as `response_time_ms`.
4. Store server-side receipt/processing timestamps separately.

Network/API latency must never be treated as learner recall latency.

The backend validates plausible numeric bounds and rejects malformed timing data, while preserving separate server-side timing for diagnostics.

## 13. Offline-First Boundary

FLUENTT is **online-first with limited offline support**.

### 13.1 Available offline

When required data has already been cached, the learner may:

- open cached lessons/vocabulary;
- complete supported basic vocabulary reviews;
- create pending local review/research events;
- view previously cached basic progress.

### 13.2 Requires connectivity

- initial authentication on a new session/device when no valid session is available;
- downloading new/updated content;
- authoritative progress synchronization;
- future NLP/conversation processing;
- future pronunciation processing;
- any operation requiring uncached server data.

## 14. Local Storage

Expo SQLite stores structured non-secret device data such as:

- cached language/content metadata;
- cached lessons/vocabulary;
- pending review attempts;
- pending research events;
- synchronization queue state;
- minimal cached progress data.

Expo SecureStore stores sensitive session/token material.

PostgreSQL remains authoritative. SQLite is never treated as the master research dataset.

## 15. Synchronization and Idempotency

Every offline-capable client event receives a client-generated UUID before it is stored locally.

Synchronization sequence:

1. Create event locally with `PENDING_SYNC` state.
2. Submit the event UUID and payload to FastAPI when connectivity is available.
3. Backend validates authorization and payload.
4. Backend checks whether that client event UUID has already been accepted.
5. If new, process/persist it transactionally.
6. If already accepted, return the existing acknowledgement/result rather than create a duplicate.
7. Mobile marks the local item synchronized only after server acknowledgement.

The server must enforce uniqueness for accepted client event IDs.

## 16. Conflict Policy

Different data categories use different conflict rules.

### 16.1 Review/research events

- Append-oriented.
- Never silently overwritten.
- Multiple genuine attempts are preserved.
- If later excluded/corrected for research purposes, the original event remains traceable and the correction/exclusion is recorded separately.

### 16.2 Learner preferences

- Server-authoritative latest valid accepted update is sufficient for v0.1.

### 16.3 Learning content

- Server is authoritative.
- Cached content is replaced only by a valid newer server version.

## 17. Research Identity and Privacy Separation

Application account data and research-facing data must be logically separated.

Account-related information may include:

- internal user UUID;
- email;
- password hash;
- account state.

Research-facing records use an internal UUID and/or participant code. Exported research datasets should use participant codes such as `P001` rather than direct identifiers such as email addresses or names.

Research event payloads must never include passwords or authentication tokens.

Raw speech retention rules are not part of v0.1 because speech processing itself is not in v0.1.

## 18. Research Events vs Application Logs

### 18.1 Research events

Used for reproducible study analysis. Examples:

- `SESSION_STARTED`
- `CONTENT_VIEWED`
- `REVIEW_STARTED`
- `REVIEW_ANSWERED`
- `REVIEW_COMPLETED`
- `SYNC_COMPLETED`

A review research record must be able to include:

- event UUID;
- participant/internal learner reference;
- vocabulary item ID;
- review/session ID;
- correctness;
- response time in milliseconds;
- item/content version metadata;
- scheduler type;
- algorithm version;
- review interval/result metadata;
- client interaction timestamp;
- server acceptance timestamp;
- device platform;
- application version.

### 18.2 Application/operational logs

Used for troubleshooting. Examples:

- exceptions;
- failed API requests;
- database failures;
- authentication errors;
- synchronization failures.

Operational logs must not be treated as the thesis dataset.

## 19. Initial Data Model

The database should contain normalized entities equivalent to the following responsibilities:

- users
- refresh/session token records
- learner_profiles
- languages
- lessons
- vocabulary_items
- learning_sessions
- review_sessions
- review_attempts
- review_schedules
- sync_events / accepted client events
- research_events

Exact table names may follow project conventions, but these responsibilities must remain represented and migration-controlled.

A review attempt must support at least:

- stable UUID;
- learner reference;
- vocabulary item reference;
- session reference;
- client event UUID/idempotency key;
- response/correctness information;
- `response_time_ms`;
- scheduler type;
- algorithm version;
- client interaction time;
- server creation/acceptance time;
- device platform;
- app version.

## 20. Error and Failure Behavior

### 20.1 Server unavailable during offline-capable review

- Persist the completed attempt locally.
- Mark it pending synchronization.
- Show a user-friendly message that progress is saved and will synchronize later.

### 20.2 Content download failure

- Do not delete usable cached content.
- Show a retryable error state.

### 20.3 Authentication failure

- Do not expose sensitive account details.
- Preserve local non-sensitive cached data unless the security/session policy requires invalidation.

### 20.4 Future AI provider failure

When AI modules are later added, a failed NLP/pronunciation call must produce a pending/failed/unavailable state, never a fabricated score or analysis.

## 21. Validation Rules

FastAPI must validate, as applicable:

- authenticated active learner;
- ownership/authorization;
- existence and active state of referenced content;
- supported language/content versions;
- valid client event UUID;
- valid response/correctness fields;
- valid numeric response-time data;
- supported scheduler identity/version;
- duplicate event status;
- request schema/version compatibility.

The client may perform usability validation, but server validation is authoritative.

## 23. Environments and Build Identity

The project recognizes four environment purposes:

- Development
- Testing
- Research
- Production (future)

v0.1 implements Development and Testing configuration and establishes the structure required for a future Research environment.

Before formal data collection, the Research build must freeze at least:

- mobile application version;
- backend commit/version;
- database schema migration version;
- scheduling/ESR algorithm version;
- content dataset version;
- research configuration.

Research data collection must not silently mix different algorithm or content versions.

## 24. Testing Strategy

### 24.1 Backend unit tests

Minimum coverage areas:

- password hashing/verification;
- token/session behavior;
- temporary-password rule;
- authorization helpers;
- scheduler interface/development scheduler;
- review validation;
- idempotency/deduplication;
- content validation;
- progress calculations.

### 24.2 Backend API/integration tests

Minimum flows:

- valid/invalid login;
- first-login password change;
- authenticated profile/preferences;
- content retrieval;
- review submission;
- duplicate retry of same client event;
- synchronization of queued review event;
- progress retrieval;
- unauthorized route rejection.

Tests must use an isolated test database/environment rather than developer research data.

### 24.3 Mobile tests

Minimum critical-flow tests:

- login state;
- first-password-change flow;
- language switching;
- lesson/vocabulary rendering;
- review interaction;
- response-time capture abstraction;
- local queue creation;
- sync success/failure state;
- logout/session clearing.

### 24.4 Research-readiness checks

Before a future research build is approved, verify at minimum:

- response time is recorded as intended;
- participant identity mapping is correct;
- scheduler type/version is recorded;
- app/content versions are recorded;
- duplicate sync submissions do not duplicate research attempts;
- offline records reconcile correctly;
- timestamps are valid and distinguish client interaction time from server receipt time.

## 25. Researcher Utilities

v0.1 requires controlled command-line/backend utilities for:

- creating a learner participant account;
- assigning/confirming a participant code;
- issuing a temporary password;
- resetting a forgotten password to a new temporary password;
- importing/seeding manually curated learning content.

A researcher/admin graphical dashboard is outside v0.1.

## 26. Explicitly Out of Scope for v0.1

The following must not be implemented as final production/research features in v0.1:

- final FLUENTT ESR equations/rules;
- conventional-SRS experimental baseline;
- experimental condition assignment/counterbalancing;
- pronunciation scoring;
- speech-recognition/pronunciation provider integration;
- NLP grammar analysis;
- conversational AI;
- AI-generated lessons;
- educator dashboard;
- administrator dashboard;
- graphical content-management system;
- advanced learner analytics;
- formal statistical analysis;
- raw speech data pipeline;
- public Play Store/App Store release;
- production-scale monitoring/billing infrastructure.

Placeholders/interfaces for later modules are allowed only when they preserve clean architecture and do not pretend the feature is implemented.

## 27. v0.1 Acceptance Checklist

v0.1 cannot be called complete unless all of the following are demonstrably satisfied:

- [ ] Monorepo structure is established and documented.
- [ ] React Native + Expo + TypeScript application runs in the supported development environment.
- [ ] FastAPI backend starts and exposes a health endpoint.
- [ ] PostgreSQL connectivity and migrations work from a clean database.
- [ ] Researcher utility can provision a learner account.
- [ ] Learner can log in with a temporary password.
- [ ] First login forces a password change.
- [ ] Authenticated sessions can be refreshed/revoked securely.
- [ ] English and Tagalog interface resources work without duplicated screens.
- [ ] Interface language and target learning language are stored separately.
- [ ] Researchers can seed/import manually curated lessons/vocabulary.
- [ ] Learner can browse/study seeded content.
- [ ] Learner can complete a basic review session.
- [ ] Device-side response time is recorded in milliseconds.
- [ ] Development scheduler returns and persists a next-review result.
- [ ] `scheduler_type` and `algorithm_version` are recorded for review events.
- [ ] Research event logging is separate from application logs.
- [ ] Cached eligible content remains usable during temporary offline operation.
- [ ] Offline review attempt enters a local pending sync queue.
- [ ] Reconnection synchronizes the pending attempt.
- [ ] Retrying the same event does not create a duplicate server attempt.
- [ ] Basic progress can be retrieved/displayed.
- [ ] Authentication secrets are not stored in SQLite/plaintext storage.
- [ ] Automated tests cover the critical backend and mobile flows.
- [ ] README documents setup, environment variables, migrations, seeding, testing, and development workflow.

## 28. Later Milestone Direction

After v0.1 is stable, future milestones may introduce:

1. conventional spaced-repetition baseline;
2. formal FLUENTT ESR implementation and algorithm versioning;
3. pronunciation processing;
4. NLP/conversation capabilities;
5. educator/researcher interfaces if justified;
6. formal experiment assignment and data-export workflow;
7. research-build freeze and pilot/formal evaluation.

Each major addition must receive its own design/implementation plan so the research contribution and supporting technologies remain separable and testable.
