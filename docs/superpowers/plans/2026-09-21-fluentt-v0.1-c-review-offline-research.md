# FLUENTT v0.1C Review, Offline Sync, and Research Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the v0.1 vocabulary review workflow, development scheduler abstraction, append-oriented research events, device-side response-time measurement, Expo SQLite offline queue, duplicate-safe synchronization, and basic progress.

**Architecture:** The phone reports interaction facts; FastAPI remains authoritative for accepted attempts and next-review state. Offline events use client-generated UUID idempotency keys. Research events are separate from operational logs. v0.1 uses a clearly labeled development scheduler only—no final ESR or conventional-SRS experiment logic.

**Tech Stack:** Existing Plan A/B stack plus `@react-native-community/netinfo`, SQLAlchemy/PostgreSQL uniqueness constraints, pytest, Jest/React Native Testing Library.

**Spec:** `docs/superpowers/specs/2026-09-21-fluentt-v0.1-design.md`

## Global Constraints

- `response_time_ms` measures learner interaction time on-device, not network round-trip time.
- The server controls scheduling state and due timestamps.
- v0.1 scheduler identity is `development`; algorithm version is `dev-0.1`.
- Offline review events are durable until acknowledged by the server.
- Re-sending the same client event UUID must not create duplicate accepted attempts/research records.
- Research events are append-oriented and separated from operational logs.
- User-facing failure messages must never fabricate review/AI results.
- Final ESR equations and conventional-SRS baseline remain out of scope.

## Review Focus

- Negative, NaN, or unreasonably large response times must be rejected rather than contaminating research data; pinned in Task 1.
- Replaying the same client event UUID after a lost acknowledgement must return the original accepted result without duplication; pinned in Task 2.
- Killing/restarting the app while offline must preserve queued review events; pinned in Task 3.
- Two queued events for the same vocabulary item remain distinct if their event UUIDs differ; pinned in Task 3/4.
- Sync authentication/session expiry must pause the queue rather than deleting pending events; pinned in Task 4.

- [ ] **Step 2: Implement immutable scheduler dataclasses/protocol**

```python
@dataclass(frozen=True)
class ReviewContext:
    correct: bool
    response_time_ms: int
    item_difficulty: float
    interaction_at: datetime

@dataclass(frozen=True)
class SchedulingResult:
    scheduler_type: str
    algorithm_version: str
    next_interval_seconds: int
    next_due_at: datetime
    state: dict[str, object]

class Scheduler(Protocol):
    def schedule(self, context: ReviewContext) -> SchedulingResult:
        raise NotImplementedError
```

Development scheduler may use a deterministic non-research rule solely to exercise workflow, for example correct -> 24 hours, incorrect -> 10 minutes. Label it explicitly non-experimental in code/docs.

- [ ] **Step 3: Write failing review-validation tests**

Backend must reject response times `< 0`, non-integers, and values above `3_600_000` ms in v0.1. This upper bound is a software sanity limit, not a research exclusion criterion.

- [ ] **Step 4: Implement review/research persistence**

`ReviewSession` stores a server UUID plus unique `(user_id, client_session_id)` so a mobile-created offline session can be reconciled without duplication. `ReviewAttempt` stores client event UUID, user/item/session refs, answer/correctness, `response_time_ms`, scheduler type/version, client interaction time, server acceptance time, device platform, app version.

`ResearchEvent` is a separate append-oriented table with event type and structured JSON payload free of passwords/tokens/email.

On successful attempt acceptance, transactionally persist:

```text
ReviewAttempt
ReviewSchedule
ResearchEvent(REVIEW_ANSWERED)
ResearchEvent(REVIEW_COMPLETED)
```

- [ ] **Step 5: Implement thin routes/service transaction and tests**

The route validates schema/auth; service owns transaction and invokes `Scheduler`. Test scheduler fields are persisted exactly as returned.

Extend the shared Plan B SQLite migrations with a `pending_review_events` table. Minimum columns:

```text
client_event_id TEXT PRIMARY KEY
payload_json TEXT NOT NULL
status TEXT NOT NULL CHECK(status IN ('pending','syncing','failed'))
attempt_count INTEGER NOT NULL DEFAULT 0
last_error TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

Do not store access/refresh tokens in SQLite.

- [ ] **Step 5: Implement review screen submit behavior**

On prompt becoming interactable, start monotonic timer. On final answer:

```text
stop timer
create UUID
create/reuse a `client_session_id`, then construct payload with client timestamp, response_time_ms, platform, app version
if online submit succeeds -> navigate to result screen with the real server scheduling result
if unavailable/network failure -> enqueue payload -> navigate to result screen showing only “saved on this device; sync pending” (no fabricated due date)
```

Do not invent a next-review result for an event that has not yet been server-accepted.

```text

same UUID retry -> no duplicate attempt/research event

scheduler_type=development and algorithm_version=dev-0.1 are persisted
```
