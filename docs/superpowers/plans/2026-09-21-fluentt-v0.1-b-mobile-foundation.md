# FLUENTT v0.1B Mobile Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the learner-facing Expo/React Native shell with bilingual localization, secure authentication, learner preferences, and manually curated lesson/vocabulary browsing against the Plan A FastAPI backend.

**Architecture:** The mobile app uses Expo Router and a small feature-oriented structure. Authentication tokens are isolated in Expo SecureStore. The app communicates only with FastAPI; no direct database or future-AI-provider connections are allowed.

**Tech Stack:** Expo SDK 57, React Native 0.86, React 19.2.x, TypeScript, Expo Router, Expo SecureStore, `expo-localization`, i18next/react-i18next, TanStack Query, Jest, React Native Testing Library, pnpm. Expo SDK 57 requires Node 22.13.x or newer; use Node 22 LTS for the project toolchain.

**Spec:** `docs/superpowers/specs/2026-09-21-fluentt-v0.1-design.md`

## Global Constraints

- Android and iOS remain code targets; Android is the primary local development/test target.
- Learner is the only mobile role.
- No public registration screen exists.
- Sensitive auth tokens go only to SecureStore, not SQLite or AsyncStorage.
- Interface language and target learning language are independent.
- English (`en`) and Tagalog (`fil`) UI resources are required.
- Learner content is read-only and server-managed.
- Final ESR, NLP, pronunciation, admin/educator UI, and formal experiment flows are out of scope.

## Review Focus

- App restart with valid SecureStore session must restore login without flashing protected content to a logged-out user; pinned in Task 2.
- A user flagged `must_change_password=true` must not navigate around the password-change route; pinned in Task 2.
- Missing translation keys must fall back to English rather than showing raw keys or crashing; pinned in Task 1.
- Unsupported server language preference must be surfaced as a recoverable validation error; pinned in Task 3.
- Empty lesson/vocabulary feeds and API failures must render deliberate states rather than blank screens; pinned in Task 4.

- [ ] **Step 1: Write failing token-store and forced-password-flow tests**

Tests must mock SecureStore and prove:

```text
login tokens are written to SecureStore
no token is written to SQLite/AsyncStorage
must_change_password=true routes only to change-password
successful password change unlocks app routes
logout deletes SecureStore session
```

- [ ] **Step 2: Implement SecureStore token adapter**

```ts
export interface TokenPair {
  accessToken: string;
  refreshToken: string;
}

export async function saveTokens(tokens: TokenPair): Promise<void> { /* SecureStore only */ }
export async function loadTokens(): Promise<TokenPair | null> { /* SecureStore only */ }
export async function clearTokens(): Promise<void> { /* SecureStore only */ }
```

Use two explicit SecureStore keys prefixed `fluentt.`.

- [ ] **Step 3: Implement API client with one refresh retry**

The client adds the access token, and on a single `401` attempts one refresh, saves rotated tokens, and retries the original request once. A second `401` clears session and returns the user to login; prevent refresh loops.

- [ ] **Step 4: Implement auth route guards**

Root auth state values:

```ts
type AuthStatus = 'loading' | 'signedOut' | 'mustChangePassword' | 'signedIn';
```

Protected navigation must depend only on this state; do not let screens manually decide authorization.

**Interfaces:**

- Produces: read-only learner study flow, server-authoritative SQLite content cache, and route to future review screen.

- [ ] **Step 1: Write failing empty/error/content-render tests**

Cover:

```text
active lessons render in server sort order
empty feed shows localized empty state
network/API error shows localized retry state
inactive content returned accidentally by a mocked API adapter is filtered defensively
vocabulary term/definition/example/version render correctly
after a successful fetch, killing network access still loads the cached lesson/items
a newer server content version replaces the cached version; an older response never downgrades it
```

- [ ] **Step 2: Implement SQLite content cache**

Use the shared `offline/db.ts` connection and migrations. Cache normalized lesson and vocabulary rows keyed by stable UUID and language. Each cached row stores `content_version`, `active`, and `updated_at`. Only a successful FastAPI response may update the cache; the client never invents or edits learning content.

- [ ] **Step 3: Implement TanStack Query content client with cache fallback**

Query keys must include target language and content version-sensitive IDs so switching target language cannot show stale content from the previous language. On a successful response, update SQLite transactionally. On network/server unavailability, return cached content for the requested language. Do not fall back to cache for authentication/authorization failures.

- [ ] **Step 4: Implement home and lesson browsing**

Home contains greeting, quick link to lessons, and placeholders only for progress fields that already have real data. Do not invent AI recommendations or fake review counts.
